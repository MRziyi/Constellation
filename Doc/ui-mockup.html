Constellation has two surfaces on the glasses, and that's it:

  1. The HUD — a transient overlay shown on top of whatever you're doing. This is where 99 % of interaction lives. (§1)
  2. The app settings — a minimal, rarely-entered configuration screen for shortcut content and the Cortex connection. (§2)

Everything about ring gestures and profiles is owned by Halo Ring — Constellation declares its actions through a plugin protocol (§3) and never touches gesture binding itself.

Visual language verbatim from R08-dev/Doc/ui-mockup.html (Halo Ring) — same eight tokens, same focus indicator, same HUD pill shape. Spec references: DESIGN.md · INTERFACE-CONTRACTS.md · UI-UX.md · halo-ring-plugin-protocol.md.

§1 The HUD — the main interaction surface

Top-right anchored, transient, dismissable. The HUD has only two atoms — a small status pill (no options) and a larger card (1–4 options). Everything below is one of these two atoms with different content. Cortex decides the icon, body, and options array per case; the glass renders.

The card is a template, not a case-specific design. The same card composable renders an email-draft preview, a face-match result, a P6 insight, a tool permission request — only icon, optional left stripe colour, body markdown, and options array differ. Anything Cortex can express as (icon, title, body, options[]) can be a card.

Atom 2 — The card (the rest of the HUD)

Every card has the same shape: [icon] [title] [v2?] / [meta] / [body markdown] / [options 1–4]. Cards differ only by: (a) icon, (b) optional 3 px left stripe (green for P6 insight, amber for P4 tool wake, none for default), (c) body content, (d) options labels. Six cases below cover the breadth.

§2 The app — minimal configuration only

You open this app to: (1) edit a shortcut's preset prompt; (2) point at a different Cortex address; (3) sanity-check connection. Nothing else is customisable — no HUD theming, no ttl knobs, no profile editing. Defaults handle everything.

What's NOT in this app. Gesture bindings, profiles, ring config, glasses settings — all of that lives in Halo Ring. Constellation has zero gesture UI of its own.

§3 Gestures & profiles — entirely owned by Halo Ring

Constellation has no gesture UI of its own. Halo Ring is the single source of truth for ring + temple gestures, profiles, mappings, system overrides — everything. Constellation integrates as a Halo Ring plugin: it declares a list of actions, and Halo Ring lists them in its existing Action Picker under a new EXTERNAL APPS group.

How a gesture reaches Constellation

  1. Wearer does a gesture (e.g. LP + SWIPE_UP) the ring sends BLE event to glasses.
  2. Halo Ring recognises the gesture, looks up the binding in the active profile, and finds it's bound to com.constellation.glass / voice_invoke.
  3. Halo Ring fires an Android Intent: sendBroadcast(Intent("com.halo.ring.action.TRIGGER") .setPackage("com.constellation.glass") .putExtra("action_id", "voice_invoke")).
  4. Constellation's TriggerReceiver wakes the foreground service, which captures photo + opens mic + builds the user_invoke event and sends it to Cortex.

What Constellation declares

A standard Halo Ring plugin ContentProvider at content://com.constellation.glass.halo_actions/list. When Halo Ring's Action Picker opens, it queries every installed plugin app for its actions list and presents them under the EXTERNAL APPS group:

action_id label group
───────────────────────────────────────────────────────────────────────
voice_invoke Voice invoke (mic + photo) CONSTELLATION
shortcut_1 Quick capture person CONSTELLATION
shortcut_2 OCR & save to today CONSTELLATION
shortcut_3 Drop a thought CONSTELLATION

Full protocol spec (manifest declarations, ContentProvider schema, Intent contract, permissions) lives in halo-ring-plugin-protocol.md — that's the document you'd hand to whoever maintains Halo Ring to implement this.

This means Halo Ring needs to add plugin discovery. The integration protocol is generic (any app can register actions), so the work isn't Constellation-specific. See the handoff prompt in halo-ring-plugin-protocol.md.

§5 Notes for implementation

  • Compose target. One foreground service (always running) hosting an overlay WindowManager view (the HUD). One ComponentActivity for the app shell (rarely entered). For RayNeo, the Activity extends Mercury SDK's BaseMirrorActivity for free binocular mirroring; for Rokid, plain ComponentActivity.
  • Theme. Reuse Halo Ring's HaloColors / HaloType tokens via a shared theme module — single source of truth across both apps. No Material default.
  • HUD overlay. Same pattern as HaloRingService.HudOverlay: WindowManager-hosted Composable, binocular re-anchor for X3 Pro (Gravity.END + 160 px inset). Constellation's preview card is wider (max 360 px) than Halo's pill — verify it fits cleanly in the right-eye region.
  • Card background. rgba(0,0,0,.86) not pure black — a touch of body to separate the card from the surrounding pixel-off region. This is the one place Constellation softens "pure black".
  • Voice Invoke pipeline. Photo + STT fire in parallel on trigger. STT is on-device (Whisper.cpp or platform STT — final pick at implementation). VAD-stop default 2 s silence; user can TAP to end early.
  • Feedback loop. Tapping FEEDBACK on a preview opens the mic without re-capturing photo (the photo on the existing invoke is reused). Cortex receives user_decision { decision: "feedback", feedback_text: "…" } and regenerates. See INTERFACE-CONTRACTS.md §1.5.
  • Halo Ring plugin integration. Implement the protocol in halo-ring-plugin-protocol.md — ContentProvider + BroadcastReceiver + manifest meta-data. Halo Ring side needs the matching discovery + Action Picker work (see same doc).
  • HUD profile auto-switch. When Constellation shows a HUD, the foreground service calls a Halo Ring API (also defined in the plugin protocol) to push the "Constellation HUD" profile onto the active profile stack. On dismiss, pop it.
  • i18n. Strings via strings.xml + strings-zh.xml. Card body is markdown; Cortex sends it pre-translated for the wearer's language.
