## 3. 实施 — 4 个 Phase

### ⚠ Testing methodology — production flow ONLY

**This is a gotcha that bit us during the first baseline session.**

Per [IN-APP-UI-DESIGN](IN-APP-UI-DESIGN.md) and Zack's stated intent: the
**MainActivity is for settings only** (QR pair, Wi-Fi adjustment, see status
once). All runtime interaction happens on the **HUD overlay** that floats
above the Sprite launcher (or whatever else is the foreground Activity).

When testing memory/energy:
- ❌ **Don't** keep MainActivity in the foreground. `am start MainActivity` is
  fine to bootstrap the Service one time, but **immediately send HOME**
  (`adb shell input keyevent KEYCODE_HOME`) so the Sprite launcher resumes.
- ✅ **Verify** with `dumpsys activity activities | grep topResumedActivity` —
  should be `com.rokid.os.sprite.launcher/.main.SpriteMainActivity`, not our app.
- ✅ **Trigger CARDs** while MainActivity is backgrounded — that's the real
  production flow.
- ✅ **Screencaps then correctly show** the HUD overlay floating above Sprite
  launcher (verified 2026-05-29 17:13: `Battery status` card with rounded
  green CardFrame visible above the Sprite "Hi Rokid" prompt).

If a screencap shows MainScreen content, it means MainActivity is in the
foreground and the overlay is being z-order-occluded — **the measurement is
invalid for "what the user actually sees during normal use"**.

### Phase α — Tooling（半天）

集成观测工具，**不改业务逻辑**。

#### α.1 LeakCanary (debug-only)

加 `debugImplementation("com.squareup.leakcanary:leakcanary-android:2.14")`。
只在 `*Debug` build 生效 — 不影响 release APK 体积。
LeakCanary 监听 `Activity` / `Fragment` / `ViewModel` / `Service` / Custom
watchers。我们关心：
- ✅ `ConstellationService`（在 onDestroy 时应被 GC）
- ✅ `MainActivity` / `LoginScreen` / `ConnectScreen` 等
- ⚠️ Custom watcher 需要给 `GlassHudOverlay` + `OverlayHostOwner` 加（不是 standard
  Android 组件，LeakCanary 默认看不到）
- ⚠️ `StateMachine` / `WssClient` / `AudioPipeline`（Long-lived singletons in scope；
  不该被 GC，**反向检查 — 验证它们没被意外重建**）

#### α.2 Memory & Process Capture Script

`scripts/glass-profile.sh`（在 Constellation 仓库的 `scripts/` 下，方便跨 session 复用）：

```bash
#!/usr/bin/env bash
# Capture memory + cpu + battery + WSS state from Rokid Glasses
# Usage: ./glass-profile.sh <label>
# Output: profile-out/<label>-<ts>.{meminfo,top,battery,dumpsys-power,logcat}
set -e
DEV=${ADB_DEV:-<glass-serial>}
LABEL=${1:-snapshot}
TS=$(date +%Y%m%d-%H%M%S)
OUT=profile-out/${LABEL}-${TS}
mkdir -p "$OUT"
echo "== meminfo =="
adb -s $DEV shell dumpsys meminfo com.constellation.glass > "$OUT/meminfo.txt"
echo "== top (5 samples, 1s apart) =="
adb -s $DEV shell top -n 5 -d 1 -b -p $(adb -s $DEV shell pidof com.constellation.glass) > "$OUT/top.txt" 2>&1 || true
echo "== battery stats =="
adb -s $DEV shell dumpsys battery > "$OUT/battery.txt"
adb -s $DEV shell dumpsys batterystats --reset > /dev/null  # for next interval
echo "== power state =="
adb -s $DEV shell dumpsys power | head -100 > "$OUT/power.txt"
echo "== wakelock =="
adb -s $DEV shell dumpsys power | grep -A2 "Constellation\|com.constellation" > "$OUT/wakelock.txt" || true
echo "== app process info =="
adb -s $DEV shell dumpsys activity processes | grep -A 30 "com.constellation" > "$OUT/process.txt" || true
echo "Saved → $OUT/"
```

## 6. Baseline measurements

### 6.1 Rokid Glasses (`<glass-serial>`) — first capture 2026-05-29 17:04-17:07

**Build**: `glass` flavor, debug, includes Compose tooling-debug + LeakCanary + ML Kit barcode.

| 测量点 | TOTAL PSS | Java | Native | Code | SWAP PSS | RSS | 备注 |
|---|---|---|---|---|---|---|---|
| cold-start (t=12s) | **95.5 MB** | 13.2 | 6.0 | 55.7 | 0.9 | 161.5 | service started + WSS connected + IDLE |
| +60s idle (HUD off) | **108.1 MB** | 13.5 | 6.3 | 64.9 | 0.5 | 166.9 | +12.6 MB; mostly Code section growth (deferred class loading); Java + Native stable |
| mid-vision-cycle | **89.6 MB** | 18.7 | 9.2 | 29.4 | **13.9** | 131.7 | CameraGate active; JPEG + b64 + JSON in flight. Kernel started swapping Code pages out (SWAP +13.4 vs cold-start) |
| +30s after vision CARD | **77.3 MB** | 9.6 | 3.5 | 32.3 | 9.9 | 124.5 | Java + Native **below** cold-start — major GC fired cleanly. HUD overlay detached (R-10 lesson). Kernel kept ~10MB code in swap |

Battery: held at 100% throughout (cold → +6min); battery readout granularity is 1% so Δ doesn't appear in this duration. Temperature 28.0°C → 28.5°C (negligible from one vision cycle).

CPU sample (cold-start +12s): 5.0% of one core; %MEM 8.9%.

### 6.2 Findings

✅ **Per-vision-cycle Java heap delta: +5.5 MB peak (13.2 → 18.7)**. Includes ~150 KB JPEG bytes + 201 KB b64 string + JSON serialization buffers. After cycle, Java drops to 9.6 MB (**below** cold-start) — GC is healthy.

✅ **Native heap delta: +3.2 MB during capture (6.0 → 9.2)**. CameraX + JPEG encoder. Returns to 3.5 MB after — also below cold-start.

✅ **No obvious leak on single cycle** — both heaps return below cold-start after the CARD dismisses + HUD overlay detaches (R-10 lesson at work).

⚠️ **Code section is volatile** (55.7 → 64.9 → 29.4 → 32.3). Backed by page cache; kernel evicts under pressure. This is fine; just means PSS varies a lot session-to-session. **Headline number**: ~60 MB code in non-swapped state — driven by Compose ui-tooling-debug + ML Kit barcode + CameraX. Debug-build APK is **58 MB** (release would drop ui-tooling + LeakCanary; ~40-45 MB estimated).

⚠️ **SWAP PSS grew to 14 MB during vision cycle** — kernel is using zram to make room. On an Android Go device with limited RAM this is the normal behavior; just means peak memory pressure happens during vision. Not a problem but watch trajectory across 5+ cycles.

### 6.2.5 ⚠ Process-life finding (2026-05-29 17:14)

When MainActivity is sent to background via HOME (production-flow methodology
— what we actually want users to do), **`com.constellation.glass` process is
silently killed** within a couple of minutes despite the FGS (type=
microphone|connectedDevice) being declared. Reproduced cleanly:

```
17:13:34 — vision CARD arrived on panel (overlay floats above Sprite launcher), proven by screencap
17:14:53 — `pidof com.constellation.glass` returns empty; ps shows no process; logcat has no FGS-kill / OOM line in the recent window
```

This is a **critical finding for C-37 (energy is #1)**: if the FGS gets killed,
WSS dies, Halo Ring `voice_invoke` broadcasts have no service to receive →
user taps ring → nothing happens. **This blocks production usability**.

Hypotheses to investigate next session:
- a) HUD overlay detach-on-Idle (R-10) triggered a Service teardown side-effect
- b) Rokid Glasses' YodaOS-Sprite has vendor-specific FGS cleanup more aggressive than stock Android 12 — would need `dumpsys deviceidle whitelist` check + battery optimization exemption
- c) Our `startForeground` notification got dismissed somehow (Rokid launcher hiding notifications?) — Android may treat that as Service no longer foregrounded
- d) Watchdog killed us during the 60s+ idle for some thermal/policy reason

**Action item**: write a `keepalive_probe.sh` that pings the WSS every 30s for
30 min in HOME'd state and reports when the connection drops. Cross-reference
with `dumpsys` to find the trigger.

For now, the design *intent* of FGS-survives-HOME is valid; the *implementation*
is breaking on real Rokid Glasses. This is **separate from C-37** (which is
about energy budget) — this is more like an "C-37b: FGS keepalive" precondition.

### 6.4 Ranked hotspots (preliminary, will firm up after more cycles)

Based on first baseline:

1. **Compose ui-tooling-debug** — adds ~5-10 MB to Code section. Already debug-only, but worth verifying it's stripped from release build via `assembleGlassRelease` once available.
2. **ML Kit barcode scanning** — 390 KB tflite model + classes ~3 MB. Used only on QR-pair Login screen. **Candidate**: lazy-load via on-demand DexClassLoader, OR replace with ZXing (smaller + offline) if barcode usage truly is one-shot.
3. **Per-cycle Java churn** — 5.5 MB peak. JPEG bytes + b64 string is the dominant cost. **Candidate**: stream b64 encoding instead of building a single string (cuts peak by ~50%; complicates the WSS send path).
4. **WSS double-emit** — Cortex sends both legacy `Command` + glass-shaped `card` for every CARD. Glass swallows legacy as no-op (since R-12 fix `edfb3ba`). **Candidate**: Cortex `_send_command` skips legacy emit when peer accepts `card`. ~30-40% in-traffic reduction; zero glass-side cost.

## 7. After P1.8 — P1.9 session router 怎么用数据

P1.8 量出来"1 个活 session 占 X MB / Y mAh/h"之后：

- 算出眼镜可用内存 - app baseline = 还剩多少给"额外 session"
- 算出每个 idle session 的 mAh/h × 期望 pin 时长（小时） = 单 session 待机电池预算
- 取 min(内存上限, 电池上限) = 推荐 pin 上限

无 P1.8 数据，P1.9 只能拍脑袋定 pin = 2 或 3，可能跑两天发现眼镜过早没电。
