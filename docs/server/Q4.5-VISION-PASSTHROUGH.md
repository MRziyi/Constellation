# Q.4.5 — Cortex vision passthrough (image-aware dispatcher)

**Created**: 2026-05-26 EOD · **Owner**: Zack · **Spec**: SoT Revision 9 / **C-47**
**Target repos**:
- `Constellation-Server/cortex/` (router + dispatcher passthrough)
- `Constellation-Server/tool-agent/` (new `vision_describe` adapter)
- `Constellation/` (this doc + SoT C-47 → landed marker after Phase 4)

**No Glass changes** — Glass already ships `image_b64` correctly per Phase Q.

---

## 1. Goal

Make image-bearing shortcuts (`whats-in-front`, `quick-capture-person`, `ocr-save-to-today`) actually work end-to-end. Today: Glass sends `{text, image_b64}` → Cortex drops the image at dispatch → tool gets "no image" → polite refusal.

After Q.4.5: image bytes flow opaquely from event → subtask `args` → new `vision_describe` tool adapter → Claude vision API → human prose back to the HUD CARD.

---

## 2. Recap of C-47 (constitutional decision, locked) — refined 2026-05-26

> **Cortex dispatcher carries image opaquely; routing decision uses prompt text only. Image flows ONLY to tools the router explicitly routed to that are declared vision-aware. Default = image goes nowhere.**

- Router/classifier read **only** the `text` field for routing decisions (they don't decode bytes; they don't even know the image's MIME type).
- The `(photo attached)` tag — already inlined into the prompt by `router._build_user_prompt:130` — is the only signal the router uses.
- Image bytes flow through `event.payload.image` and are injected into a subtask's `args` as `_image_b64` **only if the router routed to a tool in `_VISION_AWARE_TOOLS`** (a small allowlist in `cortex/server.py`, currently `{"vision_describe"}`).
- All other tools never see the image even when one is attached. This is the **"default-off"** guarantee: no surprise vision API calls just because Zack happened to fire a photo-bearing shortcut.
- The vision-aware destination is a **new** adapter, NOT a modification to `claude_code` (CC CLI is text-only today).

**Why this matters** (per Zack 2026-05-26): vision API calls cost real money; firing `claude_code` or `applescript_mail` with a 70 KB base64 blob attached just because the user *might* have wanted vision is wasteful + leaky. The router's routing decision is the gate.

## 4. Implementation — 4 phases, each independently committable

### Phase 1 — vision-tool-gated image passthrough (low risk, no new deps)

**File**: `Constellation-Server/cortex/cortex/server.py`

Module-scope allowlist:

```python
# Q.4.5 / C-47: tools that opt into receiving event.payload.image as
# _image_b64 in their args. Default = image goes nowhere. Extend when new
# vision tools land.
_VISION_AWARE_TOOLS: set[str] = {"vision_describe"}
```

In the subtask dispatch loop ([server.py:1957](../../Constellation-Server/cortex/cortex/server.py)):

```python
image_b64 = (event.payload or {}).get("image")
...
args = self._interpolate_args(st.get("args", {}), subtask_results, plan=plan)
if image_b64 and st["tool"] in _VISION_AWARE_TOOLS:
    args = {**args, "_image_b64": image_b64}
rpc_result = await self._dispatch_to_tool({**st, "args": args})
```

**Key**: the gate is `st["tool"] in _VISION_AWARE_TOOLS`. Image is NEVER blanket-injected. Router determines per-prompt whether image should flow (by choosing to route or not to route to a vision-aware tool).

**Agent path** (`_dispatch_complex_agent`) gets **no image injection** for the same reason — `claude_code` is not in `_VISION_AWARE_TOOLS`. When CC gets vision support in the future, add it to the set (one-line change).

**Done-when**:
- For vision-routed subtasks: `args["_image_b64"]` present in tool RPC payload when event carries image
- For non-vision routed subtasks (any other tool): `_image_b64` NEVER appears in args, even if image was attached
- Existing tools unchanged in behavior; image-bearing events that route to e.g. `applescript_mail` still send mail (without seeing the image)

### Phase 2 — `vision_describe` tool adapter (new file)

**File**: `Constellation-Server/tool-agent/tool_agent/adapters/vision_describe.py`

Single action: `describe`.

Args:
- `prompt: str` — user-facing instruction (e.g. "what's in front of me?")
- `_image_b64: str` (optional) — base64 JPEG bytes

Output: `{description: str, model: str, tokens: {input, output}}`

Implementation:
- Anthropic SDK direct (`anthropic.Anthropic().messages.create`)
- Model: `claude-sonnet-4-6` (vision-capable; balanced cost/quality)
- Multimodal message: `[{type:"image", source:{type:"base64", media_type:"image/jpeg", data:<b64>}}, {type:"text", text:<prompt>}]`
- System prompt: minimal — "You're describing a frame captured by Zack's AR glasses. Be concise (≤80 words), specific, human."
- Result fallback: if `_image_b64` missing/empty → `{description: "(no image attached)", ...}` — don't fail loudly, just acknowledge.

Pseudo-code:

```python
async def describe(prompt: str, _image_b64: str = "", **_) -> dict:
    if not _image_b64:
        return {"description": "(no image attached)", "model": "fallback"}
    client = anthropic.AsyncAnthropic()
    msg = await client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=400,
        system="You are describing a frame captured by Zack's AR glasses. Be concise (≤80 words), specific, human. No preamble.",
        messages=[{"role": "user", "content": [
            {"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": _image_b64}},
            {"type": "text", "text": prompt},
        ]}],
    )
    text = msg.content[0].text if msg.content else ""
    return {
        "description": text,
        "model": msg.model,
        "tokens": {"input": msg.usage.input_tokens, "output": msg.usage.output_tokens},
    }
```

Adapter registration: add to `tool_agent/tool_agent/main.py` tools dict (mirrors how other adapters are wired).

**Done-when**:
- `tool_agent` boot log shows `vision_describe` in the tools list
- `result_format` semantics: `query` (single-call bounded; result included in card body via `_render_actions_preview` summary path or surfaced as Agent finished card body)
- Anthropic API key picked up from existing `ANTHROPIC_API_KEY` env var (which Cortex already uses elsewhere — verify)

## 6. Risk register

| Risk | Mitigation |
|---|---|
| `ANTHROPIC_API_KEY` not in env (cortex uses gpt-5.2 default) | Verify before Phase 2; if missing, document in HANDOFF; user pastes key once |
| Vision API costs spiral on a hot loop | `result_format=query` is single-call; rate limit isn't our problem; budget cost = $0.003 per ~70 KB image @ sonnet rates → fine for shortcut-frequency |
| Image too large for Claude messages API | Glass already enforces 1024px / q=80 → 70 KB. Claude vision max 5 MB per image. Plenty of headroom. |
| Existing tools choke on `_image_b64` kwarg | Underscore prefix + permissive kwargs in adapter signatures. If any adapter does strict-kwarg validation we'll see it in Phase 1 tests. |
| Router over-selects vision (e.g. for "remind me to look at the photo") | Description text emphasizes "vision-shaped prompts only"; few-shot will probably need one example. Iterate if seen in Phase 4. |
| CC agent path receives `_image_b64` arg, brief schema breaks | Brief builder ignores unknown keys (we already verified this for other passthrough). Adding it is no-op until CC gets vision. |
